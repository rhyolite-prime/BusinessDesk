# Banks and branches

Apply `database/migrations/005_banks_and_branches.sql` after migrations 001–004,
then rebuild/restart the C++ backend and Nuxt frontend. The matching `.down.sql`
drops the branch table before the bank table; rollback destroys those records.

## Model and scope

The supplied C# model guides the fields and tenant ownership. Unlike the global
Currencies catalog, **banks belong to a tenant** (`IMustHaveTenant`). Tenant/user
IDs come exclusively from the verified tenant JWT, never request JSON. The
repository uses UUID tenant IDs, so the C# integer `TenantId` is adapted to UUID.

Two normalized tables replace the C# JSONB branch list:

- `core_banks`: UUID `id`, `tenant_id`, `name`, `bank_code`, `contact_person`,
  `contact_no`, `email`, and full create/update/delete audit columns.
- `core_bank_branches`: UUID `id`, `tenant_id`, `bank_id`, `name`, `contact_person`,
  `contact_no`, `email`, and the same audit columns. A composite foreign key
  ensures that a branch and its bank always have the same tenant.

Bank codes are unique case-insensitively within each tenant's nondeleted banks.
A deleted bank code may be reused. Branch names need not be unique. These are
bank directory records, not GL Bank Accounts; existing GL Bank Accounts are not
migrated or automatically linked to the new directory in this feature.

## API

All routes require `TenantJwtAuthFilter` authentication and a bearer JWT:

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/api/v1/shared/banks` | Paginated bank headers |
| POST | `/api/v1/shared/banks` | Create bank |
| GET | `/api/v1/shared/banks/{bankId}` | Bank details |
| PUT | `/api/v1/shared/banks/{bankId}` | Replace editable bank fields |
| DELETE | `/api/v1/shared/banks/{bankId}` | Soft-delete bank and its live branches atomically |
| GET | `/api/v1/shared/banks/{bankId}/branches` | Paginated branches of the bank |
| POST | `/api/v1/shared/banks/{bankId}/branches` | Create branch under that bank |
| GET | `/api/v1/shared/banks/{bankId}/branches/{id}` | Branch details |
| PUT | `/api/v1/shared/banks/{bankId}/branches/{id}` | Replace editable branch fields |
| DELETE | `/api/v1/shared/banks/{bankId}/branches/{id}` | Soft-delete branch only |

List parameters: `pageNo` (1–1,000,000), `pageSize` (1–200, default 20), `query`
(up to 160 bytes). Search is case-insensitive literal substring matching on bank
name/code or branch name. Results are ordered by name and ID for stable paging.

Bank create/update body:

```json
{
  "name": "Example Bank",
  "bankCode": "EXB",
  "contactPerson": "Jane Doe",
  "contactNo": "+233 20 000 0000",
  "email": "contact@example.test"
}
```

Branch body uses the same fields **except `bankCode`**. Parent bank comes from
the URL, not the body; branches cannot be moved between banks via update.

Name and bank code are required nonblank strings (max 160 and 40 bytes).
Contact person (160), contact number (50), and email (254) are optional strings;
omitted optional fields become empty strings, including on PUT. Values are
trimmed; nonempty email must have a basic email-address shape. UUIDs, tenant IDs,
audit/soft-delete flags, nested `bankBranches`, and all other unexpected body
fields are rejected. Record UUIDs are generated by PostgreSQL.

Responses use the existing `{success,result,error}` envelope. Lists return
`{data,totalCount,totalPages,pageNo,pageSize}`. Records expose camelCase model
fields, and branches also expose `bankId`. Create returns 201, other successful
operations 200. Errors: validation 400, unauthorized 401, missing/deleted or
foreign-tenant bank/branch 404, duplicate live bank code 409, DB/commit error 503.

All data reads/updates/deletes explicitly restrict `is_deleted=false` and the
JWT tenant. Branch operations additionally validate the live parent and constrain
`bank_id`. No host/global bank administration is introduced.

Writes use transactions and authenticated actor audit IDs. Branch mutations
lock the live parent bank first, serializing them against bank deletion. Bank
updates/deletes lock the bank row; soft deletion marks only live children, so
already-deleted children's original deletion audit remains unchanged. SQL values
are parameterized; interpolated SQL fragments are internal constants only.

## Frontend

**Shared config → Banks and branches** opens
`/ledger/shared-config/banks-and-branches`, replacing its former placeholder.
The upper table contains bank headers. Clicking a bank name selects/highlights
it and loads its branches into the lower child table. Both tables have search,
server pagination, refresh, add/edit dialogs, confirmation-based deletion,
loading/empty/error states and contact columns. Branch creation is disabled
until a bank is selected. Bank deletion warns that its branches are deleted too.

The Nuxt BFF exposes corresponding `/api/shared/banks/...` routes, forwards the
tenant bearer JWT on every upstream request, and keeps browser URLs relative.
It uses the existing ledger/auth backend-origin configuration and tenant
HttpOnly cookie; host credentials cannot substitute for tenant sign-in. Writes
use the existing same-origin protection; responses are `no-store` and upstream
errors are sanitized. Successful BFF responses unwrap `result` and return 200,
as in the existing ledger adapters. Backend field validation is authoritative.

  migration and all service SQL run against PostgreSQL, including tenant/parent
  isolation, validation, unique constraints, audit/soft deletion, rollback on
  trigger failure, commit-failure reporting and the down migration.

For the PostgreSQL test, use a **disposable** database: it creates/drops the
`bank_service_test` schema, including any preexisting schema of that name.
Configure:

```sh
BANK_TEST_DATABASE_URL='host=127.0.0.1 port=5432 user=test dbname=disposable' \
JSONCPP_SOURCE_DIR=/path/to/jsoncpp \
LIBPQ_LIB_DIR=/path/to/libpq \
bash test/banks/run_pg.sh
```

For sanitizer coverage also set
`BANK_TEST_SANITIZERS='-fsanitize=address,undefined -fno-omit-frame-pointer -g'`.
Drogon header syntax checks use actual Drogon 1.9.5 headers. The test transport is
not a running Drogon server; live C++ HTTP/JWT/DB integration, browser click
automation and multi-connection concurrency load testing remain deployment checks.
